# Task files and deliverables

## Establish one private task folder

Use the configured panel source and private DATA directory in the user-authorized environment. Read the installed CLI help and project documentation before using file operations. Keep task files outside the source repository and public Git history.

Resolve or create the existing stable task ID first. Ask the installed panel to initialize and return its task folder. Never derive a filesystem path directly from a user-supplied title or concatenate unchecked IDs. Reuse the returned folder when the task is renamed, resumed, or assigned to another executor.

The intended layout is DATA/tasks/<safe stable task key>/ with inputs/, outputs/ and tmp/. Treat the installed implementation as authoritative if its safe encoding differs.

- inputs/: authorized reference files, preserving their Library identity where applicable
- outputs/: verified reports, images, videos, archives and other deliverables explicitly registered to the task
- tmp/: disposable drafts and intermediate renders; never present these as final deliverables

Keep source code in its existing project checkout. Do not clone or move an entire repository into every task folder. Keep only requested export packages or reports as outputs. Do not scan unrelated directories or automatically import old screenshots, chats, logs or credentials.

## Produce, validate and register

1. Configure the tool's output directory under the task's tmp/ area when supported. For tools with fixed output locations, retain the returned file identity and use the supported transfer workflow; do not invent or guess output paths.
2. Preserve input originals. When Library supplies files, use the supported Library file workflow to materialize them and preserve its IDs, versions and metadata. When copying a Library-backed file, preserve metadata and do not silently create a new Library identity.
3. Validate the artifact with the relevant supported file validation workflow. Check readable text, image dimensions or rendered layout as appropriate. Do not execute an attachment merely to inspect it.
4. Register the chosen artifact with the installed panel's explicit file-import command. Let the CLI copy into outputs/ and create a non-overwriting name. Use a short descriptive title and correct file kind. Never change an old version in place.
5. Retain the actual registration result: artifact ID, stable task ID, relative path, creation time, size and content hash, plus Library ID when supported. Verify the file list for that task. Registration failure is not successful archival; retain the input and report the gap without fabricating a file entry.
6. Record a brief user-facing outcome on the same task timeline. Keep detailed content in the report rather than duplicating full files into timeline entries.
7. Deliver requested files through native chat attachments using the current Library workflow. A local file row, private filesystem path or private download URL is not proof the user can download it from their own computer.

## Names, versions and safety

Prefer an implementation-generated UTC timestamp, descriptive slug and unique suffix, with the original safe extension. Keep display titles independent of physical filenames. Use a fresh version when content changes; do not silently overwrite prior deliverables. A task rename must not rename or split its folder.

Accept only regular files under authorized access. Reject path traversal, symlinks, unexpected devices and paths outside the task's managed file area on retrieval. File previews must use supported safe formats and size limits; do not run scripts, render active HTML/SVG or open arbitrary URLs from a file record. Web metadata-only views must say so rather than showing a broken download action.

Keep temporary artifacts out of the formal file list. Do not automatically purge old files or expand sharing. Cleanup and public publication require the relevant user authorization. This skill guides tool use; it is not a filesystem watcher and cannot guarantee interception of files generated by unrelated tools or tasks.

## Verified panel CLI baseline

Verify these options against the installed CLI's help before use. SOURCE and DATA are configuration placeholders, not assumed paths.

```sh
sh "$SOURCE/scripts/start.sh" --data-dir "$DATA" task-init TASK_ID
sh "$SOURCE/scripts/start.sh" --data-dir "$DATA" artifact-add TASK_ID SOURCE_FILE --title "Readable title" --kind report --slug short-name
sh "$SOURCE/scripts/start.sh" --data-dir "$DATA" status
```

`task-init` initializes an existing registered task's folders idempotently. Read its returned folder rather than constructing one. `artifact-add` copies a regular file into outputs/ and returns the actual artifact identity, relative path, size and SHA-256. Kind allows report, image, document, data or other. Pass `--library-id` only with a verified existing Library identity; preserve local Library metadata according to the current Library workflow. `status` contains the artifacts array; filter by the exact task ID and returned artifact ID.

The current baseline accepts allowed document/image/data extensions up to 32 MiB per file. Do not split, rename or re-encode a rejected file merely to evade checks. Keep a supported Library deliverable for larger files and explain that local panel registration remains unsupported. The native viewer supports constrained PNG previews and hash-verified, read-only UTF-8 plain-text previews up to 1 MiB for supported extensions. Other types and the Web view are metadata-only. Registration is not permission to run a file, publish it, or share it with another person.
